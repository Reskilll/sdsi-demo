# Architecture Blueprint & Execution Plan: IT Service-Desk SLA Tracker

## Executive Summary
This project implements an enterprise-grade **IT Service-Desk SLA Tracker** designed for high-precision SLA breach calculation, status history tracking (including `ON_HOLD` pause management), calendar & holiday exclusions, and multi-dimensional reporting (breach rates by priority and assignee group).

The solution is architected with zero external runtime dependencies (using Python standard library for maximum portability and instant evaluation), while featuring high-performance calendar arithmetic ($O(1)$ day-block intervals rather than naive minute-by-minute loops), hardened input validation, comprehensive edge-case handling, interactive terminal reporting, JSON/CSV/HTML reporting, a synthetic benchmark generator, and automated test suites.

---

## 1. Requirements & Milestone Mapping

| Milestone | Requirement | Architectural Design |
|---|---|---|
| **M1** | SLA targets by priority: P1 (4h), P2 (8h), P3 (24h), P4 (72h) in business hours (Mon–Fri, 09:00–18:00). | Policy-driven SLA definitions; 540 business minutes per day; interval intersection arithmetic. |
| **M2** | Exclude holidays from SLA time. | Calendar abstraction (`HolidayCalendar`) supporting `YYYY-MM-DD` date lookups with zero business minutes attributed to official holidays. |
| **M3** | Pause SLA clock while ticket is `ON_HOLD`. | Event-based state transition timeline. Active vs Paused state partition. Paused intervals are excluded from elapsed time and dynamically advance the due-by wall clock. |
| **M4** | Per-ticket reporting: elapsed business minutes, due-by time, breach yes/no, breach minutes. | Comprehensive `TicketSLAResult` schema with microsecond precision, ISO-8601 formatting, and exact breach delta computation. |
| **M5** | Summary: breach % per priority and per assignee group. | Aggregation engine computing total count, breached count, breach rate percentage, average elapsed minutes, and maximum breach severity. |

## 2. Deep Edge-Case Analysis & Mitigation Matrix

| Edge Case | Description | Mitigation Strategy |
|---|---|---|
| **EC1: Created outside business hours** | Ticket created on Sunday 14:00 or Friday 21:00. | Zero business minutes accumulate until 09:00 on next working day; SLA target begins clocking from that business window start. |
| **EC2: Resolved outside business hours** | Ticket resolved on Saturday or weekday 21:00. | Elapsed time clamped at 18:00 of the preceding business day. Saturday work does not add ghost business minutes. |
| **EC3: ON_HOLD over weekend / holiday** | Ticket paused Friday 17:00 and resumed Monday 10:00. | Wall clock elapsed = 65 hrs, but business pause is strictly 2 hrs (1h Fri + 1h Mon). Due-by timestamp shifts forward by exactly 2 business hours. |
| **EC4: Rapid / Repeated State Transitions** | Multiple `ON_HOLD` $\leftrightarrow$ `IN_PROGRESS` transitions within minutes or seconds. | Chronological timeline normalization: sort transitions, dedup identical consecutive states, handle zero-width intervals cleanly. |
| **EC5: Open / In-Flight Tickets** | Ticket is not yet `RESOLVED` at evaluation time. | Configurable evaluation cut-off timestamp (`as_of`). Computes elapsed time to `as_of`, determines whether already breached or projected due-by in the future. |
| **EC6: Ticket created directly in ON_HOLD** | Initial status is `ON_HOLD`. | Clock remains stopped at 0 elapsed business minutes until first active transition. |
| **EC7: Unassigned or Missing Assignee Group** | `assignee_group` is null, empty, or missing. | Normalized to `"Unassigned"` bucket rather than throwing a key error. |
| **EC8: Multi-Day & Consecutive Holidays** | Back-to-back holidays (e.g. Thanksgiving & Black Friday) or holidays on weekends. | Set-based $O(1)$ holiday matching; weekend holidays do not result in double-deductions. |
| **EC9: Mixed Timezones & ISO-8601 Formats** | Tickets with `Z`, `+05:30`, `-04:00`, or local naive timestamps. | Unified timezone-aware normalization to target timezone (default UTC or system local). |
| **EC10: High-Volume Benchmark Performance** | 100,000 tickets with P4 (72h = 8 business days). | Analytical day-chunking formula ($O(1)$ day jumps) avoiding $O(\text{minutes})$ loops. |

## 5. Implementation Milestones & Work Breakdown

1. **Step 1: Setup Git Branch & Clean Workspace**: Check out branch `wincyvs`, ensure clean staging.
2. **Step 2: Core Domain Models & Calendar Engine**:
   - `models.py`: Strongly typed dataclasses with serialization/deserialization.
   - `calendar.py`: Fast interval calculation, business day window checks, holiday filtering.
3. **Step 3: SLA Engine & Pause Handling (M1-M4)**:
   - Timeline slicing for `ON_HOLD` intervals.
   - Elapsed business minutes computation.
   - Due-by forward projection accounting for pauses.
   - Breach status and breach minutes.
4. **Step 4: Analytics Engine (M5)**:
   - Breach % by priority.
   - Breach % by assignee group.
   - Overall health metrics (avg breach time, MTTR, etc.).
5. **Step 5: Input Validation & Sanitization**:
   - Schema validation, chronological sorting of transitions, default handling for missing fields.
6. **Step 6: CLI & Multi-Format Reporting (Terminal, JSON, CSV, HTML)**:
   - Tabular CLI with breach status color codes.
   - Self-contained HTML report with dark mode & visual summary cards.
7. **Step 7: Rich Test Suite (M1-M5 + Edge Cases)**:
   - Comprehensive test suite in standard `unittest` format with 100% pass rate.
8. **Step 8: Sample Datasets & Synthetic Data Generator**:
   - `tickets.json`, `sla_policy.json`, `holidays.json`.
   - `generate-data` CLI command.
9. **Step 9: Documentation (README.md & PROMPTS.md)**:
   - Comprehensive README with problem statement, architecture, verification steps, and run instructions.
   - Complete PROMPTS.md logging AI collaboration steps.
10. **Step 10: Git Hygiene & Verification**:
    - Atomic commits, run test suite, verify end-to-end runnability.
